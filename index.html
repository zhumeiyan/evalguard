The failure mode this catches

Your eval script runs. It exits 0. It prints a table. The numbers look plausible. Six weeks later someone discovers the baseline was never actually computed, or except: pass swallowed every real error, or recall was measured on the same corpus the model was tuned on.

Nothing crashed. That's exactly why nobody noticed. evalguard reads the source and flags those patterns before you trust the result.

Where the rules come from

Each rule traces back to a numbered entry in a 368-item failure catalogue built from ~100 experiments — mostly failures that actually happened to us, recorded with the measured number that exposed them.

Example: canon entry #23 is “a silent failure that produces a clean output is indistinguishable from success unless you check”. That single entry has now caused bugs in evalguard itself three separate times — including once where a rule was muted by a comment in the very file it was scanning. It's in the changelog.

A real report (from a real request)

The user pasted a RAG eval harness that printed ACCURACY 0.87 and asked whether the number meant anything. evalguard's reply:

evalguard free-tier report · 4 findings

| sev     | rule   | line | what                                    |
|---------|--------|------|-----------------------------------------|
| BLOCKER | EG002  | 1    | metric reported, no baseline symbol     |
| WARN    | EG005  | 9    | hits / len(cases)                       |
| BLOCKER | EG006  | 17   | bare/silent except                      |
| WARN    | EG012  | 1    | missing positive control + baseline     |

2 blocker · 2 warn

The answer to "is 0.87 good?" is: unknowable from this script. There is no random baseline, so 0.87 could be far below chance on a skewed set; and the bare except means some of those 40 cases may have failed silently and still counted as non-hits. That is the class of bug this tool exists for.

FAQ

Does this work with my framework?

It reads Python source. It doesn't care whether you use pytest, lm-evaluation-harness, a bespoke notebook, or a shell wrapper — if the evaluation logic is in Python, it scans it.

Will it flood my CI with warnings?

On correctly-written code it produced zero output. The free tier is deliberately the four highest-frequency real defects, precisely so it stays quiet on everything else.

Is the catalogue actually verified?

The entries are ours, from our own experiments. The taxonomy has not been independently validated by human annotators, and we say so in the package. What's verified is the behaviour of the tool: the detection and false-positive numbers above are reproducible from the fixtures shipped with it.
